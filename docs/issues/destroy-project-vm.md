# destroy-project-vm

**Status:** Done
**Captured:** 2026-08-10
**Started:** 2026-08-10
**Completed:** 2026-08-10

Covers two paired items: `destroy-project-vm` and
`discard-leaves-dir`. They share one decision -- whether
tearing down a VM also removes its directory on the host --
and answering it differently for the two commands would be
worse than either answer, so they are planned and shipped
together.

## Problem

**`destroy-project-vm`.** The ephemeral lifecycle is
symmetric: `scratch` creates a VM and `discard` destroys it.
The persistent one is not. `up` creates, `down` only halts,
and `reset` restores a snapshot -- nothing removes the VM.
Tearing down the `first-real-run` test VM meant abandoning
bombyx and running `vagrant destroy -f` over SSH by hand,
which contradicts the README's premise that you stay on your
workstation.

**`discard-leaves-dir`.** `discard` runs `vagrant destroy -f`,
which removes the domain and the `.vagrant` machine folder but
leaves the scratch directory itself. After
`discard pr-1234`, `~/vms/scratch/vmtest/pr-1234/` still holds
the pushed `Vagrantfile`. `README.md` says of scratch VMs that
"nothing survives, which is the point"; that is not true as
written.

## Context

### Where the change lands

| File | Change |
|------|--------|
| `crates/bombyx/src/config.rs` | reject `..` in `remote_root` |
| `crates/bombyx/src/remote.rs` | new `remove_dir` builder |
| `crates/bombyx/src/plan.rs` | `Action::Destroy`; `Discard` gains a step |
| `crates/bombyx/src/bin/bombyx/main.rs` | `Cmd::Destroy` + confirmation |
| `README.md`, `llms.txt`, `CHANGELOG.md` | document it |

`Action::Discard` currently maps to a single `vagrant_in(cfg,
&cfg.remote_scratch_dir(name), &["destroy", "-f"])`.
`Action::Destroy` is the same construction against
`remote_project_dir()`, so the command-building side is small.

### The prerequisite: `remote_root` accepts `..` today

This is the reason the work is not trivial.
`is_remote_path_char` (`config.rs:81`) permits `.` and `/`, and
nothing rejects a `..` segment. Verified live:

```
remote_root = "~/.."   ->   ssh frosti "mkdir -p ~/'../phren'"
```

Today that only misplaces a directory. With `rm -rf` in the
command set it becomes a deletion primitive:
`remote_root = "~/.."` with `project = "igor"` yields
`rm -rf ~/'../igor'`, which is the whole home directory.

`bombyx.toml` lives inside a project repo, so it is
attacker-controlled data the moment you check out someone
else's branch -- the same threat model that motivated the
`host` allowlist. Closing this must land **before** any
`rm -rf`, not alongside it.

### Constraints

- Both removal targets are built from already-validated
  parts: `project` is a checked path segment and a scratch
  name is a `ScratchName`. Only `remote_root` is loose.
- The host directory holds nothing unique. The repo is the
  source of truth, and everything in the directory was either
  pushed by bombyx or generated by `vagrant`. So removing it
  loses no operator work.
- `remove_dir` must run from outside the directory it deletes,
  after `vagrant destroy` has run inside it.

## Open questions

Both resolved -- see Decisions.

## Plan

1. **Close the traversal hole first.** In
   `Config::validate`, reject any `..` segment in
   `remote_root`, with its own error. Test it directly, and
   assert that a `..`-bearing config cannot even be parsed.
2. Add `remote::remove_dir(cfg, dir)` building
   `ssh <host> "rm -rf <quoted dir>"` via
   `quote_remote_path`. Guard it: refuse a target with fewer
   than two path segments below `~` or `/`, so a shallow
   `remote_root` cannot turn a teardown into deleting a
   top-level directory. The default `~/vms` gives
   `vms/<project>`, which passes.
3. Add `Action::Destroy` to `plan.rs`, mapping to
   `vagrant destroy -f` in the project directory followed by
   `remove_dir`.
4. Extend `Action::Discard` with the same `remove_dir` step
   after its existing destroy.
5. Add `Cmd::Destroy { project }` to the CLI, requiring the
   argument to equal `project` from `bombyx.toml` and refusing
   otherwise with a message naming what to type.
6. Update `README.md` (document `destroy`; the "nothing
   survives" claim becomes true), `llms.txt`, and add
   `CHANGELOG.md` entries.

## Test strategy

Rust unit tests for the command construction, integration
tests for the CLI surface. No new dependency, no E2E -- this
is a CLI-only project.

- **`config.rs`**: a `remote_root` containing `..` is rejected;
  `.` and `..` inside a *name* are already covered. Include
  `"~/.."`, `"../x"`, `"/srv/../.."` and a legitimate
  `"~/vms.d"` that must still pass (so the check tests
  segments, not a substring).
- **`remote.rs`**: `remove_dir` quotes the path and keeps the
  tilde expandable; the shallow-path guard refuses `~/x` and
  `/x` while allowing `~/vms/phren`.
- **`plan.rs`**: full `Vec<RemoteCommand>` assertions for
  `Destroy` and `Discard`, pinning **order** -- destroy must
  precede removal, or `vagrant` would run in a directory that
  no longer exists.
- **Integration**: `bombyx destroy` with no argument fails and
  names the project; with the wrong name fails; with the right
  name emits both commands. `--dry-run` throughout.
- **Real host**: the emitted commands change, so per Definition
  of Done item 3 this needs a real run against frosti before
  it can be called done. `--dry-run` proves the argv only. I
  will boot a throwaway VM, destroy it, and confirm both the
  domain and the directory are gone.

## Decisions

- **2026-08-10 -- Both commands remove the host directory.**
  Asked whether teardown should delete the directory, keep it,
  or remove only Vagrant's `.vagrant` state. **Chosen: both
  remove it.** The directory holds nothing unique -- everything
  in it was pushed by bombyx or generated by vagrant, and the
  repo is the source of truth -- so removal loses no operator
  work. It makes the README's "nothing survives" claim true and
  stops scratch directories accumulating one per discarded VM.
  The half-measure of keeping the `Vagrantfile` was rejected:
  it saves one cheap push on rebuild and leaves both the
  accumulation and the inaccurate claim only partly addressed.
  Accepts that `rm -rf` enters the command set, which is why
  the traversal fix is step 1 rather than a follow-up.
- **2026-08-10 -- `destroy` is confirmed by typing the project
  name.** Asked between a name argument, a `--force` flag, and
  no guard. **Chosen: the name argument**, so
  `bombyx destroy phren` proceeds only when the argument equals
  `project` in `bombyx.toml`. It reuses validation already
  present, adds no interactive prompt to a tool whose review
  mechanism is `--dry-run`, and stays scriptable. A `--force`
  flag was rejected because it is easy to reach for from shell
  history and never makes the operator name what is being
  destroyed, which is exactly the mistake worth catching --
  running `destroy` from the wrong project directory. No guard
  at all was rejected because `destroy` is not comparable to
  `down`: it discards the warm caches and installed tooling
  that the persistent lifecycle exists to preserve.

  **Partly wrong, corrected during review.** The reasoning
  about catching the wrong directory does not hold: `project`
  is read from the same `bombyx.toml` that decides which
  directory is deleted, so a repo can name itself after a VM
  you care about and the typed name proves nothing. The name
  confirmation survives as a typo guard, but the resolved
  `<host>:<directory>` is now printed on every path, because
  that is the value an operator can check independently. See
  the Outcome section.

## Outcome

`cargo xtask validate` green, 100% coverage. Nine tests added
across `config.rs`, `remote.rs`, `plan.rs` and the integration
suite.

**The prerequisite mattered.** `config.rs` now rejects a `..`
segment in `remote_root`. The test failed against the old code
first, confirming `remote_root = "~/.."` parsed cleanly and
emitted `mkdir -p ~/'../phren'`. Had `rm -rf` shipped without
this, a `bombyx.toml` in a cloned repo could have targeted a
home directory.

**The first version of the guard was wrong, in two ways the
reviewers found.** It is worth recording, because the shipped
design is the corrected one:

- It counted *textual* segments and rejected only `..`. A `.`
  segment adds a segment without adding depth, so
  `remote_root = "/."` with `project = "etc"` measured two deep
  and emitted `rm -rf '/./etc'`. Validation now rejects `.`,
  `..`, unrooted paths and roots with no real depth, and counts
  depth after dropping empty segments.
- It lived in `remove_dir`, so a root was simultaneously
  illegal to delete and legal to write: `remote_root = "/"` let
  `up` emit `mkdir -p '/etc'` and extract into it while
  `destroy` refused the same path. The rule now lives in
  `Config::validate`, so every command agrees on which roots
  are usable.

Moving it there also removed the `Result` cascade the guard had
pushed through `remove_dir`, `tear_down`, `plan` and `main`.
`remove_dir` is infallible again with a `debug_assert` as
defence in depth, and `plan` keeps its original signature.

**The confirmation was corrected, not defended.** The original
claim -- that typing the project name catches running `destroy`
from the wrong directory -- was false: `project` comes from the
same `bombyx.toml` that picks the directory, so a hostile repo
can name itself after a VM you care about. `destroy` now prints
the resolved `<host>:<directory>` on both the refusal and the
confirmed path, and the README says to read that rather than
trusting the typed name.

**Teardown is re-runnable.** An interrupted first push leaves a
directory with no Vagrantfile, where `vagrant destroy -f` fails
permanently; because teardown stops at the first failure, the
removal never ran and nothing could clear the directory. The
destroy step now skips when no Vagrantfile is present.

**Order is pinned by tests.** `tear_down` runs
`vagrant destroy -f` inside the directory and only then removes
it; reversing them would leave vagrant nothing to run in. Both
`plan.rs` and the integration tests assert the sequence, not
just its contents.

### Verified against a real host

Not inferred from a green suite. On frosti:

| Command | Result |
|---------|--------|
| `bombyx destroy` | refuses, prints `bombyx destroy phren` |
| `bombyx destroy nope` | refuses, names the mismatch |
| `bombyx destroy vmtest` | domain gone, `~/vms/vmtest` gone, disk reclaimed |
| `bombyx discard pr-9` | domain gone, `~/vms/scratch/vmtest/pr-9` gone |

In both teardowns the parent tree (`~/vms`, `~/vms/scratch`)
was correctly left in place -- only the VM's own directory went.

Changed: `crates/bombyx/src/config.rs` (`..` rejection),
`remote.rs` (`remove_dir`, `MIN_REMOVABLE_SEGMENTS`),
`plan.rs` (`Action::Destroy`, `tear_down`, fallible `plan`),
`bin/bombyx/main.rs` (`Cmd::Destroy`, `confirm_destroy`),
plus `README.md`, `llms.txt` and `CHANGELOG.md`.

### Follow-ups

- `remove_dir`'s floor is a depth heuristic, not a proof that
  the directory is one bombyx created. A stronger check would
  verify a `.vagrant` marker before removing. Not done: it
  costs an extra round trip and would refuse to clean up a
  directory whose teardown had already partly run.
